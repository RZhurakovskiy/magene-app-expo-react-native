# Magene HR Tracker — план реализации для AI-агента

## 1. Контекст

Личный проект (в первую очередь для себя, возможно позже — публикация). Мобильное приложение на React Native + Expo, которое подключается по Bluetooth Low Energy к нагрудному пульсометру Magene H64 и показывает пульс в реальном времени, а также ведёт историю тренировок.

Пульсометр отдаёт данные через стандартный BLE GATT-профиль Heart Rate Service (UUID `0x180D`), характеристика Heart Rate Measurement (`0x2A37`). Это значит, что приложение не завязано жёстко на Magene — будет работать с любым стандартным BLE-пульсометром (Polar, Garmin, Wahoo и т.п.), если он поддерживает этот же профиль.

Проверено вручную через BLE-сканер и официальное приложение Magene Utility: датчик исправен, батарея в порядке, стандартные сервисы `0x180A` (Device Information), `0x180D` (Heart Rate), `0x180F` (Battery Service) присутствуют.

### Тестовое устройство

Тестирование идёт на физическом Android-телефоне, а не на симуляторе/эмуляторе — это принципиально, потому что:

- Expo Go **не поддерживает** нативные BLE-модули в принципе.
- Симулятор/эмулятор в общем случае не имеет доступа к реальному Bluetooth-железу.

Поэтому нужен **Expo Dev Client** (кастомная dev-сборка), установленная на физический телефон через USB, а не Expo Go и не обычный симулятор.

## 2. Технологический стек

- **Expo** (SDK, актуальная стабильная версия на момент старта) в связке с **expo-dev-client** — обычный managed workflow не подходит из-за нативного BLE-модуля.
- **TypeScript** везде, функциональные компоненты и хуки.
- **React Navigation** (или `expo-router`, на усмотрение агента, если это ускорит навигацию между экранами) — стек из 4-5 экранов, без сложной вложенной навигации.
- **Zustand** для состояния приложения (лёгкий, без лишнего боилерплейта — подходит для одиночного разработчика).

## 3. Библиотеки и их назначение

| Библиотека | Назначение |
|---|---|
| `react-native-ble-plx` | сканирование, подключение и подписка на BLE-характеристики (Heart Rate Measurement, Battery Level) |
| `expo-location` | GPS-трекинг в режиме уличной пробежки (foreground + background) |
| `expo-task-manager` | фоновое обновление геопозиции, пока экран выключен/приложение свёрнуто |
| `react-native-maps` | отображение карты и трека (полилинии) в режиме уличной пробежки |
| `expo-sqlite` | локальное хранение истории тренировок (структурированные данные, нужны выборки и агрегаты) |
| `victory-native` или `react-native-gifted-charts` | график пульса в реальном времени и в истории сессии (выбрать одну, обе решают задачу, вторая проще в настройке) |
| `expo-keep-awake` | не давать экрану гаснуть во время активной тренировки |
| `zustand` | глобальное состояние (статус подключения к датчику, текущая сессия) |

Версии пакетов не фиксировать вручную — ставить актуальные стабильные, совместимые с выбранной версией Expo SDK (сверяться с `npx expo install`, а не голым `npm install`, чтобы избежать конфликтов версий нативных зависимостей).

## 4. Разворачивание проекта — это делает агент сам

Папка проекта уже создана и пуста. Агент должен самостоятельно:

1. Инициализировать Expo-проект с шаблоном TypeScript в этой папке.
2. Установить `expo-dev-client` и настроить `app.json`/`app.config.ts` (permissions для Bluetooth и геолокации на Android и iOS — `NSBluetoothAlwaysUsageDescription`, `ACCESS_FINE_LOCATION`, `ACCESS_BACKGROUND_LOCATION`, `BLUETOOTH_SCAN`, `BLUETOOTH_CONNECT`).
3. Выполнить `expo prebuild` для генерации нативных проектов (android/ios).
4. Собрать и установить dev-сборку на телефон через **EAS Build** (облачная сборка) — решение принято осознанно, не через локальную сборку. Причины: на текущем ПК не установлен Android Studio/SDK и ставить его сейчас не хочется, плюс проект может продолжиться на другом компьютере (рабочий ноутбук), где уже был неудачный опыт с установкой Android Studio. EAS Build не требует локального Android-тулчейна вообще.
   - Агент должен предупредить в самом начале этого шага, что потребуется `npx eas login` (аккаунт Expo), и подождать, если нужен ввод логина/пароля от пользователя.
   - Настроить `eas.json` с профилем сборки `development` (development client, `"developmentClient": true`, `"distribution": "internal"`) — именно под установку dev-клиента на телефон, а не под релиз.
   - Учитывать лимиты бесплатного тарифа EAS по числу сборок в месяц — пересобирать по EAS нужно будет только при изменении нативных зависимостей (добавление новой библиотеки), а не при каждом изменении JS-кода — JS правки подхватываются через `npx expo start --dev-client` без пересборки.
   - **На будущее:** если позже будет установлен Android Studio (на этом ПК или другом), имеет смысл перейти на локальную сборку (`npx expo run:android`) — это ускорит итерации при частых нативных пересборках. Переход не потребует переписывания кода приложения, меняется только цепочка сборки/деплоя на устройство.

5. Убедиться, что после сборки dev-клиент на телефоне может задеплоить JS-бандл через `npx expo start --dev-client` и в реальном времени видит изменения (Fast Refresh).

## 5. Режимы работы приложения

Два принципиально разных режима, пользователь выбирает при старте тренировки:

### Режим "Беговая дорожка" (indoor)
- Карта и GPS не нужны вообще.
- Только: подключение к пульсометру, таймер тренировки, график пульса в реальном времени.

### Режим "Улица" (outdoor)
- Всё то же самое, что в indoor-режиме, плюс:
  - GPS-трекинг маршрута (включая фоновый режим, если телефон заблокирован).
  - Отображение карты с треком в реальном времени.
  - Дистанция и темп/скорость, посчитанные по GPS-точкам.

## 6. Экраны

1. **Главный экран** — статус подключения к датчику, выбор режима (беговая дорожка / улица), кнопка "Начать тренировку".
2. **Экран подключения датчика** — сканирование BLE-устройств, фильтрация по наличию сервиса Heart Rate (`0x180D`), подключение.
3. **Экран активной тренировки** — текущий пульс крупно, живой график пульса, таймер, (карта с треком — только в outdoor-режиме), кнопка завершения.
4. **Экран итогов тренировки** (сразу после завершения) — длительность, средний/макс/мин пульс, (дистанция/темп/маршрут — для outdoor).
5. **История тренировок** — список прошлых сессий (дата, режим, длительность, средний пульс).
6. **Детали сессии** — открывается из истории, показывает сохранённый график пульса и (для outdoor) карту с маршрутом.

## 7. Модель данных (пример, агент может уточнить поля)

```typescript
interface HrSample {
  t: number; // unix timestamp, ms
  bpm: number;
}

interface RoutePoint {
  lat: number;
  lng: number;
  t: number;
}

interface WorkoutSession {
  id: string;
  mode: 'treadmill' | 'outdoor';
  startedAt: number;
  endedAt: number;
  durationSec: number;
  avgHr: number;
  maxHr: number;
  minHr: number;
  hrSamples: HrSample[];
  distanceMeters?: number;
  avgPaceSecPerKm?: number;
  route?: RoutePoint[];
}
```

Хранить в `expo-sqlite`: таблица сессий с базовыми полями для быстрых выборок в истории, плюс `hrSamples` и `route` — сериализованный JSON в отдельном поле (объём небольшой, полноценная нормализация избыточна для личного проекта).

## 8. Технические нюансы BLE, которые агент должен учесть

- Формат Heart Rate Measurement (`0x2A37`): первый байт — Flags. Бит 0 флагов определяет, идёт ли значение пульса как `uint8` или `uint16` в следующих байтах. Обязательно парсить по спецификации, а не предполагать фиксированный формат.
- На Android для BLE-сканирования обязательны runtime-разрешения на геолокацию (в старых версиях Android) либо `BLUETOOTH_SCAN`/`BLUETOOTH_CONNECT` (Android 12+) — без них сканирование молча ничего не найдёт.
- Обработка разрыва соединения с датчиком посреди тренировки — не должна ронять сессию, попытка переподключения.
- Фоновая работа (экран выключен/приложение свёрнуто) — главный риск. GPS фоновый трекинг через `expo-task-manager` нужно настраивать отдельно и тестировать на реальном устройстве, а не полагаться, что "само заработает" — на Android нужен foreground service, на iOS — background modes.

## 9. Этапы реализации

Каждый этап — отдельная логическая единица, после которой должно быть что-то рабочее и проверяемое руками на телефоне, прежде чем переходить к следующему.

1. **Bootstrap проекта** — инициализация Expo + TypeScript, установка зависимостей, настройка permissions, prebuild, первая успешная сборка dev-клиента на телефон, "Hello World" экран запускается и обновляется через Fast Refresh.
2. **BLE-подключение** — экран сканирования, подключение к пульсометру, подписка на Heart Rate Measurement, вывод сырого значения пульса на экран текстом (без дизайна). Критерий готовности: видно живой пульс с реального датчика.
3. **Хранилище** — настройка `expo-sqlite`, слой доступа к данным (создание/чтение/список сессий), без UI — просто проверка через тестовые вызовы, что запись и чтение работают.
4. **Режим "Беговая дорожка"** — экран активной тренировки: таймер, живой график пульса, сохранение сессии в БД по завершении, экран итогов.
5. **Режим "Улица" — GPS и карта** — запрос разрешений на геолокацию, трекинг маршрута через `expo-location`, отображение карты и трека в реальном времени поверх `react-native-maps`, расчёт дистанции/темпа.
6. **Фоновый трекинг** — вынести GPS-трекинг в фоновую задачу через `expo-task-manager`, проверить, что трек не рвётся при заблокированном экране.
7. **История и детали сессий** — список сохранённых тренировок, экран деталей с графиком пульса и (для outdoor) картой маршрута.
8. **Полировка и граничные случаи** — разрыв BLE-соединения посреди тренировки, потеря GPS-сигнала, пустая история, повторное подключение к последнему использованному датчику без повторного сканирования.

## 11. Стиль кода и общие правила

- TypeScript строго, без `any` без необходимости.
- Без комментариев в конфигурационных файлах (`app.json`, `eas.json`, gradle-файлы и т.п.) — пользователь их не любит и предпочитает, чтобы конфиги были чистыми.
- Не переусложнять: это личный проект для одного пользователя и одного датчика, а не платформа на миллион устройств — избегать преждевременных абстракций.

## 12. Приватность и безопасность

Приложение локальное, без бэкенда и аккаунтов — все данные (пульс, история тренировок, GPS-треки) остаются на самом телефоне. Ниже — правила, которые агент должен соблюдать неукоснительно, а не как рекомендацию "на подумать".

### Минимальные разрешения

- Запрашиваются только Bluetooth (`BLUETOOTH_SCAN`/`BLUETOOTH_CONNECT` на Android, `NSBluetoothAlwaysUsageDescription` на iOS) и геолокация (`ACCESS_FINE_LOCATION`, `ACCESS_BACKGROUND_LOCATION` — только для режима "Улица").
- Камера, микрофон, контакты, SMS, доступ к файлам вне своей песочницы — **никогда не запрашиваются**. Если какая-то библиотека тянет за собой такое разрешение через свой config plugin — это повод заменить библиотеку, а не игнорировать.
- После каждого `expo prebuild` — ручная сверка сгенерированного `android/app/src/main/AndroidManifest.xml` (и `ios/*/Info.plist`, если дойдёт до iOS-сборки): в списке permissions должно быть только ожидаемое, ничего лишнего.

### Замок на приложение

- Экран истории тренировок и детали сессии (с маршрутами) должны быть закрыты запросом биометрии/PIN через `expo-local-authentication` при каждом открытии приложения — независимо от того, разблокирован ли сам телефон в моменте. Это защищает от сценария "кто-то взял уже разблокированный телефон в руки и открыл приложение", а не только от кражи выключенного устройства (это уже покрыто штатным шифрованием ОС).

### Никакой лишней телеметрии

- Никакой сторонней аналитики, трекеров, crash-репортинга с передачей данных на сторону — не добавлять "по умолчанию" вместе с шаблоном проекта.
- Никаких логов с координатами или пульсом в консоль/файлы в релизной сборке.
- Никаких тихих фоновых сетевых запросов, не относящихся напрямую к заявленной функциональности (например, проверка внешнего IP, статуса VPN, доступности сторонних серверов и т.п.) — сетевой доступ есть у любого приложения по умолчанию без отдельного разрешения от пользователя, поэтому именно за этим агент должен следить сам, а не полагаться на то, что пользователь это разрешил или заметит. Каждый сетевой запрос в коде должен быть явно объясним: что это, зачем и куда уходит.

### Гигиена зависимостей

- Не добавлять новые npm-пакеты сверх согласованного списка (раздел 3) без явного обсуждения — в первую очередь смотреть, какие нативные разрешения/permissions пакет добавляет через свой config plugin, прежде чем ставить.
